## 結論

このプロダクトがまず完成させるべき体験は、次の2段階である。

1. 大会とカテゴリーを選べば、順位、選手、結果、ステータスをすぐ確認できる。
2. 注目選手と比較相手を選べば、どの周回で差が生まれ、失速・加速したかを正確な数値で確認できる。

新しいチャートを増やすことよりも、結果表、計算の正確性、任意比較、モバイルの入口、多人数表示の整理を先に実施する。現行の「近い最終順位を自動選択する」仕組みは分析開始を速くするため残すが、意味を明示したプリセットへ変え、任意選択を追加する。

判断原則は以下とする。

- 正しい結果を表示できない可能性は、新機能より先に解消する。
- 通常の結果確認を主導線とし、分析機能はその先へ段階的に開示する。
- 主語は「あなた」ではなく「注目選手」または選手名にする。
- 個別に色分けする比較選手は主選手を含め最大5人程度にする。
- 「全員」は全員分の着色線ではなく、結果表または集団コンテキストとして扱う。
- 新しい表示は、既存の結果表、ラップ表、タイム差、ツールチップで答えられない頻出質問にだけ追加する。
- データが周回単位なので、「どこで」は何周目までとする。コース上の場所、追い抜き時刻、失速原因は推測しない。

### 同じ問題を別の言葉で述べているもの

- 「通常のリザルト表がない」「最終結果を確認できない」「優勝者はチャート外の要約で示す」は、すべて結果閲覧の情報設計不足である。
- 「全員表示が成立しない」「似た色の線を追えない」「tooltipが長くチャートを覆う」は、多人数データを個別系列のまま表示している同一問題である。
- 「ペース低下を探せない」「1周で何秒失ったか分からない」「ギャップの傾きを目視する」は、周回ごとの得失を数値化していない同一問題である。
- 「あなたが不自然」「基準が不明」「主選手を固定すべき」は、分析の主語と役割モデルがUIに現れていない同一問題である。
- 「DNFに通常順位を表示」「欠損周回を配列位置で結合」「線を終了後までつなぐ」は、データ状態と表示意味論が分離されていない同一問題である。

### 意見の食い違いと決定

| 論点 | 食い違い | 決定 |
|---|---|---|
| 近い順位の自動比較 | 初見・総合は任意比較不足を問題視。可視化は開始負担が小さい長所と評価 | 自動比較を削除しない。「順位が近い選手」というプリセットに改名し、固定比較選手を追加する |
| 「あなた」という呼称 | 総合・初見は誤解を指摘。可視化は「自分」を中心にしたモデルを提案 | デフォルトは「注目選手」または実名。将来、本人モードが明示的に存在する場合だけ「自分」を使う |
| tooltipの有無 | 初見ではラップ点の正確なtooltipを確認できず、総合・可視化では一部動作を確認 | 「ない」と断定しない。入力方式・チャート別に再現確認し、常に正確な値へ到達できる設計に統一する |
| 現行ペースの置き換え | 総合は発散棒、初見は失速ビュー、可視化はタイム差への統合＋安定性プロフィールを提案 | まず正確な名称と説明に直し、1周得失をタイム差詳細へ統合する。失速ランキングや新プロフィールは先に作らない |
| 初期表示 | 可視化はタイム差を初期チャートに推奨。初見・総合は通常結果を先に求める | ページの初期表示は結果表。分析を開いた後の初期チャートをタイム差にする案だけ実験する |
| 全員表示 | 総合は上限、可視化は分布帯、初見は全員から対象探索を試みた | 全員への到達手段は結果表で保つ。チャートでは固定選手＋低強調の集団に圧縮し、分布帯は実験する |

## 2. レビュー自体の評価

### 信頼できる点

- 3レビューが別の観点から、結果表、任意比較、多人数表示、用語理解、正確な周回値という同じ中核問題へ収束している。
- 具体的な大会、少人数・多人数、DNF、モバイル幅を操作しており、単なる一般論ではない。
- 可視化レビューは「追加しない指標」を明示しており、チャート増加を抑える判断材料になる。
- 総合レビューは表示だけでなく、計算の結合方法とエラー復旧まで確認している。

### 割り引いて扱う点

- 実ユーザーの人数、頻度、継続率、端末比率は分からない。レビュー内の「最頻」「多数」は仮説である。
- 初見テストは1つの模擬ペルソナによる評価であり、AJOCC経験者のショートカットを悪化させないかは未検証である。
- タスクが「失速選手を探す」ように設定されているため、専用ランキングの必要性を過大評価する可能性がある。
- 公開環境とローカルHEADの同一性は保証されておらず、tooltipなど観察結果に差がある。
- 技術改善の効果は計測値が不足している。SSR、キャッシュ、動的importは妥当な候補だが、今すぐのユーザー価値は未証明である。
- 正式カテゴリー名、全ステータス、公式タイム、所属、ゼッケンが全データで利用可能かはレビューだけでは確定しない。

したがって、3レビューで一致し、低コストまたは正確性に直結する改善は採用する。一致していても大きな新機能は小さな形から始める。単独レビューの新しい分析方法は Experiment または Later とする。

## 3. ユーザーの質問から見た優先度

| ユーザーの質問 | 現在の主な障害 | 最小で有効な改善 | 優先度 |
|---|---|---|---|
| 最終結果を素早く確認したい | 選手を選ばないと順位・結果へ到達しにくい | モバイル対応リザルト表 | 最優先 |
| 特定選手のレース展開を知りたい | 検索範囲が不明、正確な周回値が見づらい | 検索範囲表示、行選択、選手サマリー、ラップ表 | 最優先 |
| 自分はどこでタイムを失った？ | 累積差の傾きや曲線を目視する必要がある | 周回別lap、前周差、比較相手との差、最大損失周の要約 | 最優先 |
| 他の選手との差はどこで生まれた？ | 比較相手を自由に選べず、1周得失が数値化されない | 任意比較＋タイム差tooltipの周回得失 | 最優先 |
| 誰がどの周回で速かった？ | 全員線の識別と正確な値の確認が難しい | ラップ表の周回最速強調＋レースfastest lap | 高 |
| 誰が後半に失速・加速した？ | 「ペース」が自己変化を表さず、多人数線が過密 | まず選択選手の前半／後半要約とラップ推移。全員ランキングは実験 | 高 |
| レースの勝負が動いたのはどこ？ | 順位と累積差を別々に目視する | タイム差に「この周で得た／失った」と順位を併記 | 高 |
| 自分と近いペースの選手は誰？ | 最終順位近傍しか選べない | 平均lap近傍の候補は有望だが、定義検証後に実験 | 中 |
| 結果は公式と同じ意味か？ | DNF、周回遅れ、更新時点、公式ソースが不明瞭 | ステータス意味論、更新日時、公式結果リンク | 最優先 |
| 同じ分析を後で開く・他人へ見せたい | 状態がURLに残らない | 安定した選択状態をクエリへ同期 | 高 |

レビューに明示されていないが、「このデータはいつ更新され、公式結果とどう違うか」「表示された差は欠損や周回遅れを正しく扱っているか」という信頼性も重要なユーザーニーズである。分析機能では、派手な機能より信頼できる定義が継続利用を左右する。

- Confidence: 3レビューの一致、観察の再現性、データ実現可能性への確信

| 「結果だけ見る」専用モード | 結果表を初期表示し分析を段階開示すれば不要。モード追加は状態と説明を増やす |
| ペース低下ランキングの即時追加 | 失速定義が未確定で、単一の異常周回と持続的失速を混同しやすい。まずラップ表と選択選手の要約で検証する |
| cumulative time、fastest lap、前周差、平均差を別々のチャートにする | 既存のタイム差・ラップと目的が重複し、タブと学習負荷だけが増える |
| 全選手へ固有色を割り当てて全線を表示する | 色数を増やしても識別・タップ・凡例の問題は解決せず、色覚多様性にも弱い |
| 全ステータスを推測で先に実装する | DNS、DSQ、OTL等が実データでどう表現されるか未確認。存在する状態と公式意味を調査してから型を決める |
| 周回データからコース上の追い抜き地点や失速原因を表示する | 現行データでは判断できず、誤情報になる |
| 66大会の一覧を今すぐ仮想化する | 現規模ではYAGNI。検索性とモバイルレイアウトが先 |
| 4つ以上の分析要約を常時大きなカードで表示する | モバイルで結果とチャートを押し下げる。最初は2〜3個の小さな要約で十分 |
| 複雑な安定性チャートで現行ペースを直ちに置換する | 中核体験を整える前には実装・説明・検証コストが大きい。EX-3として需要確認後に判断する |

## 5. 依存関係

主要な順序は次のとおり。

```text
データ契約・実データ状態の確認
  ├─> lapNumber結合・有効周回定義・変換テスト
  │     ├─> 正確なラップ表／fastest／平均／最大得失
  │     ├─> タイム差の周回得失
  │     └─> 類似ペース／安定性の実験
  └─> ステータス意味論
        └─> リザルト表と選手サマリー

比較状態モデル（主選手・固定比較・プリセット・集団）
  ├─> 任意比較UI
  ├─> 多人数チャートの役割別表示
  └─> URL同期
```

追加の依存関係は以下。

- 結果表はステータスと公式タイムの定義を確認してから列仕様を確定する。
- 派生指標を追加する前に、全表示で共通の「有効周回」を決めて単体テストする。
- 現行ペースを削除する場合は、1周ごとの得失がタイム差の詳細で同等以上に確認できることを先に検証する。
- URL同期は比較状態モデルが安定してから行い、古いURLや不正値のフォールバックも定義する。
- 集団分布帯、類似ペース、安定性プロフィールは、個別比較と基本チャートの利用テスト後に判断する。
- SSRやキャッシュは、現行Next.jsのローカルガイドを確認し、実測した性能・障害状況から設計する。

## 6. 最終ロードマップ

### Phase 1 — Foundation / Quick Wins

1. `lapNumber` 結合、有効周回、欠損、周回遅れ、終了点の定義を固定し、変換ロジックのテストを追加する。
2. 実データのステータスを調査し、DNF等を公式順位・最終通過順位・差から分離して表示する。
3. モバイル大会一覧を縦型または2段行にし、大会名と大会見出しを横方向に切らない。
4. 順位・選手・結果・ステータスに絞ったレスポンシブなリザルト表を追加し、行から分析へ進めるようにする。
5. 「あなた」を「注目選手」または実名へ変え、カテゴリー正式名・人数、検索範囲、比較プリセットの意味を表示する。
6. 選手検索を空白・全半角・大文字小文字で正規化し、利用可能なら所属・ゼッケンも対象にする。
7. フォームラベル、主要タップ領域、focus-visible、コントラスト、非色依存の選択状態を修正する。
8. カテゴリー変更時の比較状態、エラー再試行、404・一覧復帰を予測可能にする。
9. 順位をステップ線、他の周回系列を直線＋実測点にし、欠損を接続しない。

Phase 1だけでも、入口、最終結果、データ信頼性、初見理解、モバイル操作が明確に改善する。

### Phase 2 — Core Experience

1. 主選手、固定比較選手、順位近傍プリセット、集団を分けた比較状態モデルを導入する。
2. 検索で任意の比較選手を追加・削除できるようにし、個別系列を主選手込み最大5人程度にする。
3. チャートを役割別スタイルへ変え、主選手を強調、固定比較だけを色分けし、その他を低強調にする。
4. 「タイム差」を中核分析にし、累積差、当該周回で得た／失った秒、周回終了順位を同じ詳細で示す。
5. 選手のラップ表と、fastest lap・平均lap・最大得失周のコンパクトな要約を追加する。
6. モバイルのチャート詳細をチャート下の固定領域へ出し、hover、tap、keyboardで同じ情報へ到達できるようにする。
7. 一覧フィルターと分析状態をURLへ同期し、戻る・再訪・共有を成立させる。
8. 公式結果リンク、非公式表示、更新日時・対象期間を、利用可能なメタデータに合わせて追加する。

### Phase 3 — Advanced / Experimental

1. タイム差を分析の初期チャートにする案を、小規模なユーザーテストまたは利用計測で比較する。
2. 全員線の代わりとなる集団中央値・四分位帯を試し、理解速度と誤読を検証する。
3. 類似平均ペースの比較候補を試し、最終順位近傍より実際に選ばれるか確認する。
4. ペース／安定性プロフィールは、後半失速・安定性・近いペースの需要が確認できた場合だけ試作する。

Phase 3は検証結果が弱ければ実装しない。Laterの項目も利用データやデータ量の変化がない限りロードマップへ昇格させない。

## 8. 実装前に確認すべきこと

レビューだけで仕様を決めず、以下を先に調査する。

1. レビュー対象URL、プロジェクト文書に記載された公開URL、ローカルHEADが同一のデプロイか。正規の本番URLも確定する。
2. 全大会・全カテゴリーのJSONで、公式順位、総合タイム、トップ差、所属、ゼッケン、ステータス、周回遅れ、公式結果URL、更新日時がどの程度揃うか。
3. `finished` / `dnf` 以外のDNS、DSQ、OTL等が実際に存在し、収集側でどう表現されるか。表示順と公式順位の意味も確認する。
4. 欠損 `lapNumber`、1周目以外から始まる記録、同一周回重複、0秒、異常値、DNF、周回遅れを全データから抽出し、件数とパターンを把握する。
5. 最初の記録を除外する現行ルールが全大会で妥当か。fastest、平均、前半／後半を計算する「有効周回」をデータ収集側と合意する。
6. DNFの「トップ差」が離脱時点で計算可能か、公式値か派生値か。派生値ならUI上で明示できるか。
7. ラップtooltipが出ないケースを、チャート別、マウス、キーボード、タッチ、ブラウザ別に再現する。公開版とローカル版の差も確認する。
8. カテゴリー正式名称・対象・統合カテゴリーの説明を、信頼できるデータまたは管理可能なマッピングから取得できるか。推測の名称は使わない。
9. リザルト表でモバイルに常時出す列を、実データの長い選手名・所属・タイム・DNF・68人規模で試作検証する。
10. 「昇格圏」の定義、対象カテゴリー、`—`になる条件を確認する。説明できない場合は表示自体を再検討する。
11. 比較上限を4人か5人のどちらにするか、3〜8人・15人以上の実レースで識別性とタップ操作を確認する。
12. 首位基準切り替え、類似ペース、全員分布、安定性プロフィールへの実需要を、少数の競技者・応援者・初見者のタスクテストで確認する。
13. URLへ保存する状態、デフォルト値、不正値、存在しない選手、カテゴリー変更時、ブラウザバック時の仕様を先に定義する。
14. 色・文字コントラスト、タップ領域、キーボード順、スクリーンリーダーでのチャート代替情報を実ブラウザで確認する。
15. SSR、キャッシュ、動的importを行う前に、実端末の初期表示、JS転送量、データ取得失敗率、検索流入、OG共有需要を計測する。

## 最終判断

最も避けるべきなのは、失速ランキングや新しい分析チャートを先に増やし、通常結果、比較相手、モバイル入口、データ正確性が未完成のままになることである。

まず Phase 1 で「正しく、見つけやすく、結果をすぐ読める」状態にする。次に Phase 2 で「選びたい相手と、どの周回で差が生まれたかを正確に読める」状態にする。Phase 3は、基本体験では答えられない需要が実際に確認できたものだけ実施する。この順序が、ユーザー価値、保守コスト、YAGNIのバランスが最もよい。
